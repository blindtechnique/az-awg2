# Changelog

Все заметные изменения проекта. Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), версии — по [SemVer](https://semver.org/lang/ru/).

## [3.0.0-beta.5] — 2026-08-27 · ветка `beta`

### Добавлено

- **Приёмка переехала в репозиторий, появился CI.** Наборы писались по ходу работы и жили вне git — на машине автора: проверить изменение мог только он, а сторонний участник не имел ни одного способа убедиться, что ничего не сломал. Теперь они лежат в `tests/`, запускаются одной командой `bash tests/run.sh` и гоняются на каждый push и pull request.

  Наборы намеренно разбирают **настоящие файлы репозитория**: блоки вырезаются из скриптов на лету, обработчики бота вызываются как есть с подставным Telegram, а команда для фонового юнита не сверяется со строкой, а действительно запускается на подставных `awg-obfuscation`/`awg-client`. Проверено, что прогон краснеет: возврат старого конвейера `systemctl list-unit-files | grep -q` и возврат сравнения с веткой `main` роняют его именно на тех наборах, которые за это отвечают.

  В CI добавлен запрет CRLF по всему дереву — на этом проект ломается раньше всего, а установщик чистит `\r` только у того, что раскладывает сам.

### Исправлено

- **Обратная сторона `--reapply`: пути, которые просят новый профиль, его не получали.** Пункт меню «Обновить обфускацию (новый профиль с текущими настройками)» предупреждает, что конфиги придётся раздать заново, берёт подтверждение — и не выставлял `RECONFIGURE`, то есть после правки выше молча ничего не менял. Владелец соглашался отключить всех и не получал ничего. То же с явным `--preset X`: он минует меню, `RECONFIGURE` оставался нулём, новый пресет записывался в `install-state.env`, а `obfuscation.env` оставался прежним — и `awg-obfuscation --show` начинал врать про пресет. Оба пути теперь выпускают профиль, как и обещают.

  Защита от перевыпуска ценна ровно настолько, насколько работают пути, которые перевыпуск просят: иначе вместо «конфиги не ломаются» получается «профиль не меняется никогда», и ротация обфускации при блокировках тихо перестаёт работать.

- **Подсети слоя 2.0 закрепляются так же, как порты.** `AZ_SUBNET`/`VPN_SUBNET` пересчитывались из конфига ванильного AntiZapret на каждом полном прогоне. Пока ваниль стоит на своём диапазоне, результат тот же, но её переезд увёл бы сервер, а у всех выданных клиентов остался бы прежний `Address` — `regen-all` этого не чинит, он адреса не трогает. Теперь закреплённое значение из `services.env` сильнее вычисленного, как это давно сделано для портов.

- **Обновление слоя перевыпускало профиль обфускации и отключало всех клиентов.** `gen_obfuscation` всегда звал `awg-obfuscation.sh --apply`, а тот генерирует **новый случайный** профиль. То есть любой полный прогон установщика — переход с `main` на `beta`, повторная установка, автоматизация без терминала — обрывал связь всем выданным клиентам сразу. От этого спасал единственный узкий случай: пункт меню по умолчанию уводит в `--update`, где стоит ранний возврат до `gen_obfuscation`. Защитой это не назовёшь: достаточно было запустить установщик с любым флагом, минующим меню.

  Появился режим `--reapply`: существующий профиль раскладывается заново, значения не меняются. Новый профиль выпускается **только** по явному `--reconfigure`. Файл профиля проверяется для каждого слоя отдельно — общая проверка по чужому перевыпускала бы клиентов на пустом месте. В `awg3` такой режим был с самого начала; здесь его просто не было.

  README при этом советовал для перехода между ветками именно `--reconfigure` — то есть ровно тот путь, который всех и отключал. Совет исправлен.

- **`regen-all` не был идемпотентен.** Блок обфускации вставляется перед `[Peer]`, но хвостовые пустые строки секции `[Interface]` оставались, и после вычистки старых ключей их становилось на одну больше. Каждый следующий прогон добавлял ещё одну: содержательно конфиг не менялся, а файл — менялся, и владелец видел «конфиги пересозданы» там, где не изменилось ничего.

- **`regen-all` теперь говорит, скольким придётся переимпортировать.** Раньше он печатал по строке на каждый конфиг — на сотне людей сотни строк, из которых не следовало главного. Теперь в конце: `Конфиги клиентов: 87 без изменений — переимпорт не нужен`, а при настоящем изменении названы и число, и имена.

- Появился набор приёмки `tests/test_migration_main_to_beta.sh`: он прогоняет клиентский конфиг через обе версии слоя и сравнивает побайтно и файл, и ссылку `vpn://`, и проверяет, что профиль не перевыпускается. Проверено, что набор краснеет: возврат «всегда `--apply`» и возврат накопления пустой строки роняют его каждый на своей проверке.

- **Кнопка «Проверить обновления» горела вечно на установке с `beta`.** Ветку помнит `.layer-branch`, но её читал только `awg-upstream-check.sh` — а кнопка в боте зовёт другой путь кода, `az_setup_runner.py check-updates`, и тот сравнивал ревизию слоя с веткой `main`, зашитой в умолчание `_remote_head(repo, branch="main")`. На beta-сервере ревизии не совпадали никогда: бот сообщал об изменениях, обновление ничего не меняло, кнопка загоралась снова. Проверено на боевом сервере: `.layer-rev` и `refs/heads/beta` совпадали байт в байт, а бот всё равно показывал обновление.

  Теперь ветка берётся из `.layer-branch`, а при его отсутствии восстанавливается из `AWG_INSTALL_SH_URL` в `bot.env` и записывается на диск — как и в `awg-upstream-check.sh`.

- **Бот не объяснял, почему приложение пишет «version 3.1».** Слой работает на AmneziaWG 3.0 (`amneziawg-go v3.0.20260805`), и 3.1 не используется намеренно, но приложение Amnezia с версии 5.0 считает версию протокола само и знает ровно одну тройку — 3.1; строки «3.0» в нём нет вовсе, а любой непустой параметр слоя 3 (у нас это `HeaderProtectionKey`) сразу даёт «version 3.1». В README это было описано, а человек, получивший конфиг и открывший приложение, видел расхождение без объяснения. Теперь пояснение приходит вместе с конфигом слоя 3.0 — там, где расхождение и встречается. Подписи слоя намеренно **не** переименованы: они соответствуют тому, что реально работает.

- **`--apply` возвращал 0, даже когда профиль не доехал до туннеля.** Вызывающий — бот, установщик, `&&` в командной строке — спокойно шёл дальше и раздавал клиентам конфиги от профиля, которого на сервере нет. Ровно это и произошло у владельца вручную. Теперь такой исход возвращает код 3: «в файлы легло, до работающего туннеля не доехало».

  Ругаться при этом можно только там, где есть чему ломаться. На первой установке юнитов ещё нет — их ставит `switch_services` уже **после** обфускации, — интерфейсы не подняты, и молчание здесь норма: скрипт спокойно сообщает, что профиль применится при первом старте, и возвращает 0. Установщики код 3 переносят (сервисы поднимаются строчкой ниже), а любой другой ненулевой код по-прежнему валит установку.

- **Бот определял исход операции по хвосту лога.** `regen-all` печатает по строке на каждый клиентский конфиг — на сотне человек это сотни строк, и предупреждения обфускатора гарантированно выпадали из окна. Случай «юнит не найден» не проверялся вовсе, а сообщение об ошибке уверяло, что «конфиги клиентов НЕ трогались», хотя интерфейсы к тому моменту могли быть уже перезапущены. Теперь юнит пишет исход в отдельный файл, и различаются четыре состояния: применено; применено, но демон не подтвердил параметры 3.0; сервер обновлён, а `regen-all` упал (клиенты без связи — сказано прямо, с командой для повтора); профиль не применён вовсе.

- **Кнопка перевыпуска сигнатур отключала всех без единого вопроса.** Она зовёт `--regenerate`, а тот сам ставит `APPLY=1` и перезапускает интерфейсы — радиус поражения тот же, что у смены пресета. Работала синхронно в обработчике callback (бот на минуты становился глухим, Telegram обрывал запрос), с таймаутом 180 секунд на `regen-all`, который на сотне клиентов не укладывается, и с отброшенным кодом возврата. Теперь у неё тот же экран последствий и тот же фоновый юнит.

- **Смена профиля из бота стирала домен и MTU.** Команда собиралась без `--regenerate`, поэтому `host`, `mtu` и `fp` брались из умолчаний скрипта, а не из сохранённого профиля: после первой же смены пресета `META_HOST` пустел, а `META_MTU` обнулялся навсегда. Теперь `--regenerate` передаётся всегда — явный `--preset` его перекрывает, ради этого и делался приоритет флагов.

- **Счётчик «затронуто людей» показывал ноль при ошибке.** `awg-client list` мог упасть, а бот отбрасывал код возврата и выводил успокоительный `0` ровно тогда, когда со слоем что-то не так. Теперь неизвестное число так и называется.

- **README обещал Debian 12.** Планку задаёт не слой, а сам AntiZapret: его `setup.sh` читает версию через `lsb_release` и выходит с кодом 5 на Debian младше 13 и с кодом 6 на Ubuntu младше 24. То есть на Debian 12 базы просто не будет, и слою не на чем работать — обещание было невыполнимым. Значок и раздел «Требования» приведены к Debian 13+, добавлено объяснение, откуда планка берётся. Комментарий в интеграции про «проверено на Debian 12/13» поправлен по той же причине.

## [3.0.0-beta.4] — 2026-08-26 · ветка `beta`

### Добавлено

- **Обфускация настраивается отдельно для слоя 2.0 и слоя 3.0.** Раньше пресет спрашивался один раз и применялся к обоим, хотя «интенсивность» значит для них разное: `router` и `low` объявлены без header protection, паддинга и таймингов, и на них слой 3.0 отдаёт ровно то же, что 2.0 — отдельный слой теряет смысл. Установщик теперь задаёт второй вопрос и **прямо предупреждает** об этом; полный набор 3.0 начинается с `medium`. Неинтерактивно: `--preset3 X` и `--template3 Y`.

  Совместимость сохранена: если значение не задано, слой 3.0 настраивается как 2.0 — именно так вели себя все прежние установки, и молча менять им профиль нельзя.

- **Порты слоя 3.0 можно задать вручную.** Раньше `--awg-ports` действовал только на 2.0, а порты 3.0 всегда выбирались случайно, и повлиять на это было нечем. Появился `--awg3-ports A,V`, а в интерактивной установке порты спрашиваются для каждого слоя. Приоритет: явно заданный сильнее закреплённого, закреплённый — сильнее случайного. Пересечение портов между слоями ловится сразу, а не всплывает потом как «Address already in use» на старте второго интерфейса.

- **Список клиентов стал постраничным** — по 10 на страницу, с навигацией и счётчиком «стр. N/M». По краям листается по кругу: с первой страницы «назад» уводит на последнюю, так до хвоста добираться одним нажатием. В подписи указано, сколько всего клиентов и какие из них показаны.


- **Список админов бота меняется без переустановки:** `install.sh --bot-admins 111,222,333`. Бот читает `AWG_BOT_ADMINS` один раз при старте процесса, поэтому достаточно переписать строку и перезапустить юнит — venv, зависимости и токен не трогаются. Работает на обеих исторических раскладках: и когда настройки лежат в `bot.env`, и когда они остались строками `Environment=` в самом юните. Список **заменяется целиком** — перечислять надо всех, включая себя.

  Значение проверяется до записи: пустая строка или мусор в списке отвергаются с кодом 2. Иначе бот стартовал бы с пустым `ADMINS` и не отвечал бы никому, включая владельца.

- **Смена пресета обфускации переехала в меню «🛡 Обфускация» и обзавелась подтверждением.** Раньше она пряталась в «🔄 Обновление», а кнопка «Сменить 2.0» в самом меню обфускации пресет не меняла — она лишь перевыпускала сигнатуры внутри прежнего. Теперь «🎲 Новые сигнатуры» названы своим именем, а рядом стоит «🛠 Сменить пресет».

  Перед применением показывается экран последствий: сколько человек потеряют доступ, что конфиги придётся раздать заново, что второй слой и порты не затрагиваются. Прежде выбор шаблона применял профиль **сразу** — одно случайное нажатие отключало всех клиентов слоя без единого вопроса. При выборе `router` или `low` для слоя 3.0 бот отдельно предупреждает, что на них слой вырождается в 2.0.

  Сама операция ушла в фоновый transient-юнит с живым логом: смена профиля перезапускает интерфейсы, а `regen-all` на сотне клиентов идёт минутами — в обработчике callback бот всё это время был глухим, а Telegram успевал оборвать запрос. Юнит заодно служит замком: второй админ получает отказ, а не гонку. `regen-all` выполняется **только** при успешной смене профиля, иначе клиентам раздались бы конфиги от профиля, который на сервер не лёг.

### Исправлено

- **Смена профиля обфускации не доезжала до работающего туннеля.** `awg-obfuscation --apply` печатал «Применено» и «Готово», но интерфейсы не перезапускал: наличие юнита проверялось конвейером `systemctl list-unit-files | grep -q`, а под `set -o pipefail` он возвращает 141. `grep -q` выходит по первому совпадению и закрывает читающий конец трубы, systemctl получает SIGPIPE на остатке вывода — и весь конвейер считается упавшим. `set -e` при этом молчит, потому что команда стоит в условии `if`.

  Для слоя 2.0 это означало, что сервер живёт на прежней обфускации, хотя в конфиге лежит новая. Для слоя 3.0 — хуже: его параметры (header protection, паддинг, тайминги) живут только в памяти `amneziawg-go` и применяются из `<iface>.v3` на `ExecStartPost`. Без перезапуска они не применялись вовсе, и диагностика честно писала «параметры 3.0 не применены», а владелец запускал команду снова и снова с тем же результатом.

  Срабатывало через раз, и не из-за объёма вывода: на замере (systemd 259, 344 юнита, 22 КБ — вчетверо меньше буфера трубы) гонку создаёт хвостовая строка «N unit files listed», которую systemctl пишет отдельно, уже после того как grep нашёл совпадение в 24-й строке и закрыл трубу. Ненулевой код выпадал в 31 прогоне из 60, условие оказывалось ложным в 34 из 60, а вычислялось оно дважды за запуск — так что «ни одной строки Перезапуск» это рядовой исход, а не экзотика. `--no-legend` и `grep -m1` проблему не снимают. Проверка наличия юнита теперь делается без конвейера (`systemctl cat`), а её отрицательная ветка **говорит вслух**, а не пропускает работу молча.

- **Диагностика спрашивала только один интерфейс слоя 3.0 из двух.** Проверялся `antizapret-awg3`; `vpn-awg3` про header protection не спрашивали никогда. Полный туннель мог сколько угодно работать как 2.0 — доктор об этом молчал, а в сумме с пропущенным перезапуском это и держало проблему невидимой. Теперь опрашиваются оба, и в отчёте видно, у какого именно ключа нет.

- **Диагностика не отличала «ключа нет» от «спросить не удалось».** Отсутствие `awg3-uapi.py`, мёртвый UAPI-сокет и честно пустой профиль давали один и тот же вердикт — владелец чинил не то. Теперь у каждой причины свой текст. Заодно убрана проверка бита `+x`: скрипт запускается через `python3`, и потерянное право на исполнение выдавало «параметры не применены» на исправном сервере.

- **Настройки слоя 3.0 не доходили до генератора обфускации.** В `gen_obfuscation3` комментарий стоял между `\` и командой, поэтому перенос строки рвался: префикс окружения `AWG3_AZ_CONF=… AWG3_VPN_CONF=…` превращался в обычное присваивание в текущей оболочке и до дочернего процесса не доходил. Спасали только совпадающие значения по умолчанию — при любом переименовании интерфейсов профиль лёг бы не туда. Заодно строка лога показывала пресет слоя 2.0 вместо выбранного для 3.0.

- **Добавлена проверка, что параметры 3.0 приняты демоном.** После перезапуска скрипт спрашивает их обратно через UAPI и, если `header_protection_key` не вернулся, пишет об этом прямо, с командой для разбора. Прежде расхождение «в файлах новое, в туннеле старое» снаружи было не видно совсем.

- **`--preset` при `--regenerate` молча игнорировался.** Команда вида `awg-obfuscation --v3 --preset medium --regenerate --apply` заканчивалась строкой `preset=low`: блок регенерации подгружал сохранённые метаданные и перезаписывал ими **все** переменные, включая только что разобранные из командной строки. Сменить пресет существующему слою было нечем — оставалось стирать `obfuscation3.meta` руками. Теперь разбор аргументов помечает то, что задано явно, и метаданные заполняют только незаданное. То же касается `--template`, `--fp`, `--host` и `--mtu`.

- **Проверка обновлений сравнивала beta-сервер с веткой `main`.** Ветку помнит файл `.layer-branch`, но установки, сделанные до его появления, его не имеют, а откат по умолчанию вёл на `main`. Расхождение веток вечное, поэтому «есть обновление» горело всегда, а нажатие кнопки ничего не меняло. Теперь при отсутствии файла ветка восстанавливается из `AWG_INSTALL_SH_URL` в `bot.env` — того самого URL, который кнопка «Обновить слой» и дёргает, — и сразу записывается на диск, чтобы чинить это один раз.

- **Бот называл слоем «AWG 2.0» то, что обновляет оба слоя.** Кнопка, заголовок, строка диагностики и оба финальных сообщения говорили про 2.0, хотя `install.sh --update` пересобирает и слой 3.0 тоже. Владелец слоя 3.0 не понимал, чем ему обновляться. Везде теперь «AWG 2.0/3».

- **Карточка клиента в боте показывала данные одного случайного интерфейса.** У части людей не было ни трафика, ни онлайна, ни IP, ни города с провайдером, ни истории подключений — при том что топ-5 по трафику в «Информации о сервере» их видел.

  Одно имя — это несколько peer'ов с разными ключами: у ванильного AntiZapret их сразу два (`antizapret` и `vpn`), у нашего слоя тоже бывает два. `client()` брала строку запросом `LIMIT 1` без сортировки, то есть первую по rowid, и дальше считала по ней **всё**: трафик, онлайн по её `last_handshake`, адрес и гео по её `endpoint`, историю подключений по её `pubkey`. Если человек ходил через полный VPN, а первой оказывалась запись `antizapret`, карточка показывала нули при живом трафике.

  С боевого сервера: у одного клиента `antizapret` даёт 0 МБ, `vpn` — 92.2 МБ, и **обе записи с handshake**. У другого порядок оказался удачным — поэтому у него всё отображалось, и баг выглядел выборочным. Топ-5 не страдал, потому что считает `JOIN`'ом по всем строкам сразу.

  Теперь карточка суммирует все интерфейсы клиента внутри слоя: трафик складывается, handshake берётся максимальный, адрес и слой — у самого свежего peer'а, история подключений объединяется по всем ключам. Добавлена разбивка по интерфейсам — без неё не видно, каким конфигом человек реально пользуется, а какой лежит мёртвым грузом. Слои при этом по-прежнему не смешиваются.

- **Пересозданный клиент показывал бы чужой трафик.** `del_client` не трогает `stats.db`, поэтому строка удалённого peer'а остаётся в базе навсегда. Само по себе это было безвредно, пока карточка брала одну строку, но суммирование сложило бы трафик нового клиента с трафиком его удалённого тёзки. Теперь в сумму идут только peer'ы, которые есть в серверных конфигах; если живых не осталось вовсе, история всё равно показывается — иначе она пропадала бы вместе с клиентом.

- **Диагностика пугала исправный сервер.** На пресетах `router` и `low` доктор писал «параметры 3.0 не применены — профиль работает как 2.0», хотя оба пресета объявлены с `header_protection=False`, `content_padding=None` и `timings=False`: ключа там нет **по замыслу**, а не из-за поломки. Владелец шёл искать несуществующую проблему.

  Теперь проверка смотрит на пресет из `obfuscation3.meta`. Для `router` и `low` это спокойная строка «так и задумано» с подсказкой, как перейти на полный набор 3.0. Для `medium`, `high` и `paranoid` отсутствие ключа — по-прежнему предупреждение, но теперь с указанием, где искать: `obfuscation3.env` (`AWG_HPK_HEX`) и файл `<iface>.v3`. Если метаданных нет вовсе, предупреждение тоже остаётся — молчать в неизвестной ситуации хуже.

- **Счётчик «👥 Клиентов» считал строки, а не людей.** `COUNT(*) FROM peers` — это записи, а у одного человека их несколько (ваниль заводит клиента сразу в `antizapret` и `vpn`), плюс удалённые клиенты остаются в базе навсегда: `del_client` её не чистит. На сервере с 85 людьми выходило 126. Теперь считаются люди, живущие в серверных конфигах, а число конфигов показывается рядом: `👥 Клиентов: 85 (126 конфигов) · онлайн 12`. «Онлайн» тоже стал считать людей, а не peer'ов — человек с двумя активными туннелями учитывался дважды.

- **Слой 3.0 мог не опрашиваться вовсе.** Если в `services.env` нет строки `LAYER3=` — а на установках, поднятых до появления слоя, её нет, — жёсткий дефault `"0"` молча выключал опрос: карточки 3.0 оставались пустыми навсегда, и понять причину было нельзя. Теперь при отсутствии строки слой определяется по наличию его конфигов; явное значение в `services.env` по-прежнему сильнее.

- **Часть клиентов не попадала в список бота.** Список рисовался одним экраном со срезом `[:80]`, и на сервере, где записей под девяносто, хвост отбрасывался молча — без единого намёка, что показано не всё.


- **`--install-bot` требовал заново вводить токен, чтобы добавить одного админа.** Прошлые значения искались только в systemd-юните, а установщик как раз выносит их оттуда в `bot.env` с правами 600 (юнит в `/etc/systemd/system` читается всеми). На такой установке `prev_token` и `prev_admins` всегда оказывались пустыми: обещание «Enter = оставить текущее» не работало, а Enter приводил к выходу с кодом 2. Теперь действующие настройки читаются по цепочке `bot.env` → `install-state.env` → юнит, и токен спрашивается, только если его действительно негде взять.

- Та же ошибка в `setup_bot()`: при переустановке слоя поверх бота, поставленного через `--install-bot`, значения не находились и бот молча пропускался.

- **Датапас слоя 3.0 не обновлялся никогда.** Мешали сразу два независимых блокиратора: `install_awg3()` выходила по проверке «бинарник на месте», не сверяя версию, а из ветки `--update` она вообще не вызывалась. В сумме `amneziawg-go` навсегда оставался той версии, с которой сервер поставили, сколько бы раз ни запускали обновление. Теперь сверяется ревизия исходников, а `--update` пересобирает датапас и перезапускает юниты `awg3@`, если версия действительно сменилась.

- **Проверка обновлений сообщала о несуществующем обновлении бесконечно.** Установленная версия сравнивалась с последним тегом апстрима, а проект намеренно держится серии 3.0 — расхождение было бы всегда: бот шлёт уведомление, `--update` ничего не меняет (см. пункт выше), уведомление приходит снова. Теперь обновлением считается расхождение с пином, а свежий тег апстрима показывается отдельной справочной строкой. Версия `amneziawg-tools` показывается без пометки «есть обновление»: они ставятся пакетом из PPA вместе с ванильным AntiZapret и отдельно от него не обновляются.

- Переменная `AWG_TOOLS_REF` объявлялась, но не использовалась нигде — читатель считал, что версия утилит зафиксирована, хотя это было не так. Убрана вместе с объяснением, откуда утилиты берутся на самом деле.

### Исправлено в коде

### Исправлено в документации

Проверены все 13 строк таблицы диагностики и остальной README — по коду проекта и по исходникам клиентского приложения (тег 5.0.1.5). Верными оказались четыре строки, остальные переписаны.

Оба утверждения неверны: подпись ставится строго по отсутствию флага `isThirdPartyConfig`, а импорт `.conf` выставляет его сам — то есть Legacy может прийти **только** из ссылки. Команды `awg-client regen-all` в README не было ни разу, хотя именно её зовут бот и установщик.

## [3.0.0-beta.2] — 2026-07-26 · ветка `beta`

### Исправлено

- **Установка обрывалась на первой же строке: `: invalid option nameset: pipefail`.** Файлы попали в репозиторий с Windows-машины, где git отдаёт рабочую копию с CRLF, а загрузка через веб-интерфейс GitHub сохраняет их как есть — и `bash` читал `set -euo pipefail\r`. Установщик вдобавок вычищает `\r` из склонированного репозитория перед раскладкой, чтобы одна неудачная загрузка не ломала установку целиком.
- **Бот создавал клиента 2.0 вместо 3.0 и потом не мог отдать файлы.** Разбор аргументов `awg-client add` знал только сервисы `antizapret` и `vpn`, а всё незнакомое молча выбрасывал — запрос на `antizapret3` превращался в обычного клиента слоя 2.0 в чужом каталоге. Теперь сервисы слоя 3.0 распознаются, а неизвестный аргумент — это явная ошибка, а не тишина.

Слово «Legacy» приложение подставляет само, когда контейнер называется `amnezia-awg`, а флаг `isThirdPartyConfig` не выставлен: так оно отличает конфиги своего мастера установки от чужих. При импорте `.conf` приложение ставит флаг самостоятельно, а в ссылке `vpn://` его обязан проставить тот, кто ссылку собирает. Теперь подпись — «AmneziaWG (version 2)». Версии «3» приложение по-прежнему не знает: в его исходниках есть только 1.5 и 2, поэтому «version 2» — это максимум, который оно способно показать и для конфига 3.0. Параметры 3.0 при этом передаются и применяются.
- Самотест конфигов проверяет `isThirdPartyConfig` — эта же подпись больше не уедет к пользователю незамеченной.
- `awg-client add` для split-туннеля падал молча, если в системе нет `/etc/wireguard/ips`: под `set -e` подстановка возвращала 1, и скрипт умирал без единой строки в выводе.

- **Слой 3.0 не поднимался: `awg3@…` падал с «control process exited with error code».** Интерфейсы слоя 3.0 создаются с плейсхолдером `__AWG3_OBFUSCATION__`, а скрипт обфускации вырезал из конфига только вариант без тройки — плейсхолдер оставался в `[Interface]`, и `awg setconf` отказывался читать конфиг на нераспознанной строке. Так как `setconf` вызывается из `ExecStartPost`, systemd сообщал лишь о неудаче control-процесса, не показывая причину. Теперь плейсхолдер вырезается в обоих написаниях, датапас дополнительно отфильтровывает его сам и при отказе `setconf` пишет в журнал настоящую строку ошибки.
- **Установщик печатал «Слой 3.0 поднят» сразу после сообщения о том, что он не стартовал.** Итог теперь соответствует факту, а при неудаче в вывод попадают последние строки журнала каждого юнита.
- **Диагностика в боте приезжала сырым текстом** — с ANSI-раскраской, которая в Telegram превращается в мусор вида `[1;32m`, и без структуры. Бот берёт у `awg-doctor` машинный вывод и рисует сам: разделы, статусы кружками, итог отдельной строкой. Так же оформлен и самотест конфигов.
- **Ложное замечание про DNS.** Проверка требовала `view:addr` для подсетей полного VPN, хотя ванильный AntiZapret их для себя не заводит — вставлять было некуда, а `awg-doctor` каждый раз ругался. Теперь свой view спрашивается только там, где он есть у ванили.
- **DNS-view для подсетей слоя 3.0 не добавлялись** — `awg-knot-view.sh` знал только подсети слоя 2.0, поэтому `awg-doctor` постоянно сообщал, что в `kresd.conf` не хватает view для двух подсетей. Теперь скрипт обрабатывает подсети обоих слоёв.
- `awg-knot-view.sh` вызывается и при установке одного лишь слоя 3.0 (раньше — только вместе со слоем 2.0).
- Вывод `awg-doctor --json` снова содержит заголовки разделов, поэтому диагностика в боте рисуется с разбивкой, а не сплошным списком.
- Карточка клиента подписывает слой по его происхождению (2.0 / 3.0 / сток), а не всегда «AmneziaWG 2.0».
- `awg-selftest.py` находит экспортёр рядом с собой, а не только по пути установки: скрипт можно запускать прямо из репозитория.

## [2.1.1] — 2026-07-26

### Исправлено

- Приложение Amnezia VPN показывало импортированный конфиг как **«AmneziaWG Legacy»** (то есть 1.0/1.5) вместо 2.0. Причина не в самом конфиге: при импорте `vpn://` приложение не вычисляет версию протокола, а читает готовое поле `protocol_version` из контейнера, и пустое значение трактует как легаси. Теперь экспортёр проставляет версию по той же логике, что и импортёр клиента: есть `S3` и `S4` → `2`, иначе только I-пакеты → `1.5`. Поле влияет не только на подпись в интерфейсе — от него зависит, будет ли клиент подставлять свои дефолты для `S3`/`S4`.

  Исправление действует на ссылки, созданные **после** обновления. Для уже выданных клиентов ссылки пересобираются командой `awg-client regen-all` — после неё «📥 Скачать конфиг» в боте отдаст исправленную `vpn://`, которую нужно переимпортировать на устройстве. Ключи, порты и профиль обфускации при этом не меняются, поэтому работающие туннели переподключать не требуется — до переимпорта они просто продолжают показываться как «Legacy».
